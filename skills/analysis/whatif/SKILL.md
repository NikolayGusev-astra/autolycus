# WhatIf — Premortem Skill

## Что это

Premortem — техника от психолога Гэри Кляйна (Harvard Business Review, 2007).
Вместо того чтобы гадать, что пойдёт не так **после** провала, мы представляем,
что план **уже провалился** через 6 месяцев, и работаем назад — ищем причины.

**Ключевое открытие:** Когда спрашиваешь «что может пойти не так?» — люди дают
осторожные, общие ответы. Когда говоришь «это уже провалилось, объясни почему» —
мозг переключается в нарративный режим и выдаёт конкретные, неудобные, честные причины.

Wharton и Cornell называют это «prospective hindsight» — доказано повышает
способность выявлять причины будущих неудач.

**Зачем агенту:** По умолчанию агент склонен к оптимистичным, соглашательным ответам.
На вопрос «это хороший план?» он найдет причины сказать «да». Premortem ломает паттерн —
агент ищет не почему план сработает, а почему он развалился.

## Когда запускать

**Хорошие цели:**
- Продукт или фича, которую собираетесь строить
- Запуск с деньгами или репутацией на кону
- Изменение ценообразования или бизнес-модели
- Кандидат, которого собираетесь нанять
- Стратегический или позиционный разворот
- Партнёрство или сделка
- Кодовый патч / PR / коммит с потенциальными side-эффектами (изменение констант,
  флагов, условных веток, затрагивающих все модели/провайдеры)
- Любое обязательство, где цена ошибки высока

**Плохие цели:**
- Расплывчатые идеи без конкретного плана (сначала помогите спланировать)
- Вопросы с одним правильным ответом
- Запрос креативной обратной связи по черновику (это редактура, не премортем)
- Решения, которые уже приняты и необратимы (премортем полезен, пока можно изменить курс)

## Процесс

### Шаг 1: Сбор контекста (minimum bar)

Premortem настолько хорош, насколько хорош контекст. Размытый ввод → размытые сценарии провала.

**⚠️ Обязательный pre-check: реальные связи пользователя**
Перед генерацией причин провала проверь wiki (entities/), memory (user profile) и session_search на реальных контрагентов, партнёров и ongoing проекты пользователя. Premortem без учёта существующих контактов — анализ абстракции, а не реальной ситуации.

Пример (May 2026): Premortem «внедрение Астра Linux» не учёл партнёра (Алексей Сидорюк, Ассоциация ФинТех) — что полностью меняло: канал продаж, competitive moat, распределение нагрузки. Исправление потребовало перезапуска.

**Правило:** При бизнес-плане/стартапе — сначала проверь или спроси:
- Кто твои реальные партнёры/контакты?
- Какие из них могут быть каналом продаж?
- Какие у них компетенции (продажи, технологии, отрасль)?
- Какие ongoing проекты/продукты уже есть?

**Нужно три вещи:**
1. **Что это?** — Чёткое понимание объекта премортема (продукт, запуск, найм, стратегия). Должно формулироваться в одно предложение.
2. **Для кого / кого затрагивает?** — Аудитория, клиент, команда, стейкхолдеры. Сценарии провала сильно зависят от того, кто вовлечён.
3. **Как выглядит успех?** — Какой результат пользователь хочет получить. Провал определяется инверсией успеха.

**Откуда брать контекст:**
- Текущий диалог — пользователь мог обсуждать план, запуск, продукт ранее в сессии
- Workspace — CLAUDE.md, memory/, файлы, которые пользователь явно прикрепил
- Google Docs / Docs ссылки — curl -sL -A "Mozilla/5.0" "https://docs.google.com/document/d/DOC_ID/export?format=txt" --max-time 30 > /tmp/source.txt; читай через read_file или cat
- HippoRAG / session_search / LLM Wiki — если тема поднималась в предыдущих сессиях
- Не трать больше 30 секунд на сбор. Глубокий контекст можно докупить через агентов.

Если всего достаточно — сразу к премортему. Если чего-то не хватает — спроси.
Один вопрос за раз. Не устраивай допрос.

### Шаг 2: Установка фрейма

После сбора контекста явно установи фрейм:

> «Ок, контекста достаточно. Запускаем премортем. Представь: прошло 6 месяцев. [План/запуск/решение] провалился. Всё. Мы оглядываемся назад и пытаемся понять, что пошло не так.»

Этот фрейм переключает режим с «оцени план» (соглашательство) на «объясни, почему это сдохло» (честное выявление причин).

### Шаг 3: Генерация причин провала (raw premortem)

Один комплексный анализ. Без категорий, без ограничений. Чистый метод Кляйна:

> «Этот план провалился через 6 месяцев. Сгенерируй ВСЕ реальные причины, по которым он мог умереть. Будь конкретен. Каждую причину привязывай к деталям плана. Не разбавляй слабыми причинами и не останавливайся рано, если их больше.»

Каждая причина провала должна быть:
- **Специфична для этого плана** (не generic совет)
- **Привязана к деталям**, которые пользователь предоставил
- **Реальной угрозой** (не мелким неудобством и не крайне маловероятным кейсом)

Количество: сколько есть на самом деле. У одного плана может быть 4 причины, у другого 9.

### Шаг 4: Deep-dive агенты (один на причину, батчами по 3)

Каждую причину провала отдаём отдельному sub-agent. Из-за ограничения `max_concurrent_children=3` (конфигурация агента), причины >3 нужно разбивать на батчи по 3-4 причины:

- batch 1: F1, F2, F3
- batch 2: F4, F5, F6
- batch 3: F7, F8, F9, ...

Все задачи внутри батча запускаются **параллельно**. Последовательный спавн тратит время и позволяет ранним ответам влиять на поздние. Батчи — компромисс: три волны, каждая parallel.

**Промпт для sub-agent:**
```
You are an investigator in a premortem analysis. You've been assigned one specific failure
reason to analyze in depth.

The plan:
--[full context: what it is, who it's for, what success looks like, plus relevant workspace context]
--
PREMORTEM FRAME: It is 6 months from now. This plan has failed.

YOUR ASSIGNED FAILURE REASON: [the specific failure reason from step 3]

Your job is to go deep on this one failure. Write the story of how it actually played out. Be specific. Use details from the plan. Make it feel real, like a case study of something that actually happened.

Your output should include:
1. THE FAILURE STORY: A 2-3 paragraph narrative of how this specific failure played out. Use details from the plan. Name specific moments where things went wrong and why.
2. THE UNDERLYING ASSUMPTION: The one thing the user was taking for granted that made this failure possible. State it in one sentence.
3. EARLY WARNING SIGNS: 1-2 concrete, observable signals the user could watch for that would indicate this failure mode is starting to play out. These should be things you can actually see or measure, not vague feelings.

Keep the total response under 300 words. Be direct. Don't hedge. Don't sugarcoat.
```

**ВАЖНО (May 2026): Sub-agent deep-dives могут фейлиться** — упираться в `max_iterations` (50 вызовов инструментов) или таймаут (600s), т.к. саб-агенты уходят в исследование кода вместо простого анализа.

**Fallback при фейле sub-agent:**
1. Если затаймился или упёрся в max_iterations — **не перезапускай**
2. Синтезируй напрямую из raw причин (шаг 3), используя свой собственный анализ
3. Для этого достаточно 3 вещей: почему причина реальна, какое допущение стоит за планом, какие ранние сигналы
4. Формат отчёта тот же — синтез как если бы deep-dive сработали
5. Качество будет ниже, но лучше чем бесконечный ретрай

**Как предотвратить фейл:**
- Укажи sub-agent в промпте: «DO NOT research the codebase. This is pure analysis. 2-3 paragraphs max.»
- Если видишь что sub-agent делает search_files/session_search — это признак что он ушёл в ресёрч вместо анализа
- Для технических деталей укажи в промпте все нужные факты, чтобы sub-agent не лез в код

### Шаг 5: Синтез

После того как все агенты завершили работу, прочитай каждый deep-dive и собери синтез:

**ПРЕМОРТЕМ-ОТЧЁТ**

1. **Самый вероятный провал** — какой сценарий наиболее вероятен? Почему? На этом пользователь должен сфокусироваться в первую очередь.
2. **Самый опасный провал** — какой сценарий нанёс бы наибольший ущерб, даже если он менее вероятен? От этого стоит застраховаться.
3. **Скрытое допущение** — какое самое большое допущение делает пользователь, которое он, вероятно, даже не подвергал сомнению? Часто это самая ценная часть премортема.
4. **Пересмотренный план** — какие конкретные изменения сделают план более устойчивым? Будь конкретен. Не «подумай о ценообразовании», а «протестируй цену $X на 20 человеках до публичного объявления».
5. **Чеклист перед запуском** — 3-5 конкретных вещей, которые пользователь должен проверить, протестировать или внедрить до начала.

### Шаг 6: Генерация отчёта

Создай два файла:

1. **`premortem-report-[timestamp].html`** — визуальный отчёт для просмотра
   - Тёмный фон (#0a0e1a), чистый шрифт
   - Синтез наверху (самый вероятный / самый опасный / скрытое допущение / пересмотренный план / чеклист)
   - Карточки для каждой причины провала: заголовок, стори, допущение, ранние сигналы
   - Разные accent colors для каждой карточки
   - Индикатор серьёзности/вероятности для каждого сценария
   - Футер с timestamp и что премортили
   - Открой HTML после генерации

2. **`premortem-transcript-[timestamp].md`** — полный транскрипт для референса
   - Собранный контекст (что, для кого, критерии успеха)
   - Raw причины провала
   - Все deep-dive от агентов
   - Полный синтез

### Шаг 7: Краткое резюме в чат

Выдай 3 предложения в чат:
- Самый вероятный провал
- Скрытое допущение
- Самая важная правка плана

Детали — в отчёте.

## Complementary analysis (pre-processing)

Для продукт-решений (ADR, стратегия, запуск) премортем даёт максимальный эффект, если перед ним провести структурный анализ плана:

1. **Записать ADR** — формализовать решение: контекст, альтернативы, обоснование, риски
2. **Prism-full анализ ADR** — multi-pass structural analysis с adversarial pass. Вскрывает скрытые допущения, нестыковки, экономические разрывы
3. **Premortem** — на выходе из Prism уже есть список слабых мест. Премортем их углубляет и добавляет нарративные сценарии провала

Этот пайплайн (ADR → Prism → Premortem) даёт: формальное решение + структурный анализ + нарративные сценарии = полная картина рисков. Результат: /root/wiki/adr-xxx.md + /root/wiki/prism-adr-xxx-analysis.md + /root/wiki/premortem-report-xxx.html

### Multi-option screening pipeline: Prism on N → select → Premortem

Когда пользователь предлагает **несколько вариантов** (например, «5 идей бизнеса на 200k») и нужно выбрать лучший для Premortem — используй **трёхфазный pipeline с параллельным Prism-скринингом**:

**Фаза 1: Отбраковка (с пользователем)**
- Пользователь называет N вариантов (обычно 3-5)
- Спроси: «Какие варианты явно отпадают?» — пусть сократит до 2-4
- Причина: Premortem фатального варианта тратит время, пользователь часто сам знает что не взлетит

**Фаза 2: Параллельный Prism-скрининг**
- Запусти **один `delegate_task` с N задачами** (по одной на каждый вариант)
- Каждой задаче: полный контекст варианта + навыки исполнителя + бюджет/ограничения
- Инструкция: «Проведи структурный Prism-анализ этого варианта — найди conservation law, главные риски, deepest finding»
- **`toolsets=[]`** — саб-агенты не должны уходить в исследование, это чистый анализ из контекста
- Все N запускаются параллельно (одним вызовом `delegate_task(tasks=[...])`)
- После завершения: собери результаты в **сравнительную таблицу** (Time-to-cash, Budget adequacy, Moat, Risk level, Critical findings)

**Фаза 3: Premortem на выжившего**
- Покажи пользователю таблицу и спроси «Выбираем этого?»
- После подтверждения — полный Premortem (Шаги 2-7)
- Если Premortem выявил фатальные риски — вернись к следующему кандидату из таблицы
- Если все кандидаты отбракованы — сообщи пользователю и предложи generate новые варианты

**Пример из практики (2026-05-11):** 5 вариантов бизнеса → пользователь отбросил 2 (VPN и MOEX-сигналы) → параллельный Prism 3 вариантов (White Label AI, Telegram-боты, Астра Linux) → сравнительная таблица → выбран Астра Linux → Premortem выявил 8 фатальных причин → план пересмотрен с «ИП-одиночка» на «субподряд интегратора».

**Когда НЕ использовать:** Если вариантов слишком много (>6) — сначала попроси пользователя сократить. Если варианты 1-2 — сразу Full Prism + Premortem.

### Обратный порядок (Premortem → Prism)

Допустим и обратный порядок, когда премортем запускается первым (быстрый скан рисков), а затем Prism adversarial pass углубляет findings и может переопределить execution plan.

**Пример из практики (2026-05-05):** Premortem на план «делегировать subagent'у сбор хардверной информации с козаноута» выявил 8 причин провала, включая F4 (subagent fake success) и F8 (включение WiFi убьёт SSH). Prism adversarial pass задал вопрос «зачем вообще делегировать, если у тебя есть прямой SSH?» — и execution план изменился с «запустить subagent» на «сделать самому через SSH-команды».

Result: premortem → prism → direct execution (no subagent). Premortem выявил риски, prism сказал «это неправильный подход», execution изменился. 

**Когда работает:**
- Когда план — «делегировать / запустить subagent» — премортем быстро выявит риски делегации
- Когда премортем нашёл больше 5 причин — стоит добавить prism adversarial pass, а не сразу deep-dive агентов
- Когда решение проще чем кажется — prism может сказать «делай в лоб, без делегации»

См. также references/google-docs-fetch.md — как добывать контекст из Google Docs для анализа.

## Важные правила

- **Всегда спавнить всех failure agents параллельно.** Последовательный спавн тратит время и позволяет ранним ответам влиять на поздние.
- **Batch если лимит concurrent.** Если `max_concurrent_children` в config.yaml меньше числа failure modes — разбить на batch'и по 3 (или сколько разрешено). Не запускать последовательно все — это искажает результаты. Batch-и независимы, результаты сводить после всех batch'ей.
- **Всегда явно устанавливай фрейм премортема.** «Это уже провалилось» — психологический механизм, который заставляет это работать.
- **Будь комплексным, но без понтов.** Найди все реальные причины провала. Не останавливайся на 3, если их 7. Но не высасывай 7, если их только 3.
- **Синтез — это продукт.** Большинство прочитают синтез и пролистают карточки. Сделай синтез конкретным и применимым.
- **Не подслащивай.** Смысл премортема — сказать пользователю то, что он не хочет слышать, до того, как реальность скажет ему это сама. Если у плана серьёзные проблемы — говори прямо.
- **Пересмотренный план должен быть конкретным.** Не «подумай о тестировании цены», а «запусти пилот за $47 на 20 человеках до полного запуска за $297».
- **Minimum bar контекста обязателен.** Премортем на размытом контексте даёт generic причины, которые тратят время пользователя.
- **Самый ценный finding — скрытое допущение.** Не останавливайся на очевидных рисках (F1-F8). Глубокий finding обычно виден только после adversarial pass: «план — это wish-логика, а не execution-логика». Главный риск не в технологии, а в том, что план не оставляет space для ошибок, итераций и восстановления.
- **Ресурс-реалити чек обязателен.** Сопоставь объём работ (человеко-часы) с доступным ресурсом исполнителя. Если соотношение >1.5x — это finding, а не деталь. Используй таблицу: работа | время по плану | реальное время (с hidden complexity). Hidden complexity factor 3-5x — норма для планов с 1-строчными пунктами.
- **Это не LLM Council.** Council даёт множественные перспективы на решение прямо сейчас. Premortem отправляет агента в будущее, где решение уже провалилось, и работает назад. Если пользователь хочет множественные перспективы, а не анализ провала — предложи council вместо этого.
- **«Сказал А, говори и Б.»** Если анализ выявил проблему или узкое место — НЕ останавливайся на диагнозе. Предложи полное решение в том же сообщении. Пользователь явно требовал: «ты определил следующее узкое место, почему не пошел дальше?»

## Пример

**Пользователь:** «premortem this: запускаю живой воркшоп за $297 по Claude Cowork для маркетинговых команд. 50 мест. Цель — маркетинг-менеджеры в компаниях 10-50 сотрудников.»

**Raw premortem:** 6 причин провала:
1. Маркетинг-менеджерам в таких компаниях нужно утверждение $297, вы не учли этот фрикшн
2. «Claude Cowork для маркетинга» — тул-специфичная подача, когда рынок ещё не разобрался с AI
3. Реальная аудитория — солопренёры, а не тим-менеджеры
4. Для демо-сред нужны реалистичные маркетинговые данные и multi-seat setup — 5 недель, а вы заложили 2
5. Если 60% придут солопренёры — ваши кейсы не резонируют с целевой аудиторией будущих потоков
6. $297 × 50 = $14,850 — не окупает подготовку

**Синтез:** Самый вероятный — мисматч аудитории (нужно утверждение $297). Самый опасный — солопренёры вместо менеджеров, что ломает будущие когорты. Скрытое допущение — «маркетинг-менеджеры в компаниях 10-50 человек» — достижимая аудитория, но они не идентифицируют себя так и не тусуются в одних местах. Правка: пилот $47 на 20 человеках, выяснить кто реально придёт.

## Code-Change Premortem (вариант для техпатчей)

Премортем кодового патча (строка/константа/флаг) — не то же самое, что
премортем продукта. Паттерны провала другие, синтез короче, HTML-отчёт
не нужен. См. `references/code-change-premortem.md`.

**Отличия от обычного премортема:**
- Шаг 1 (контекст): прочитать код вокруг изменяемых строк — обязательно
- Шаг 3 (raw причины): использовать типовые failure patterns (F1-F8) из
  references/code-change-premortem.md — они повторяются от патча к патчу
- Шаг 4 (deep-dive): ПРОПУСТИТЬ. Причины узкие, subagent не нужен
- Шаг 6 (отчёт): ПРОПУСТИТЬ. HTML не нужен. Всё в чат
- Синтез: F1+F2 (точность ветки и симптом vs корень) — всегда главные.
  F3 (upstream override) — если форк. Остальные — по контексту

**Чеклист перед вливанием (из F1-F9):**\n- [ ] Я точно знаю, в какую ветку кода уходит выполнение при проблеме?\n- [ ] Этот патч лечит причину, а не симптом?\n- [ ] Если это форк — как патч выживет при следующем merge с upstream?\n- [ ] Константа подходит для всех провайдеров/моделей?\n- [ ] Есть тест, который упадёт если патч откатят?\n- [ ] Есть лог/телеметрия, показывающая что патч сработал?\n- [ ] Стоимость (токены/деньги/время) не выросла скрыто?\n- [ ] Скрытое допущение проверено (нет ли обратной связи, ослабляющей эффект)?\n- [ ] **Арифметика:** промежуточные вычисления реально достигают нового капа? Если\n  `base = 4096` и `retry = 3`, то boost никогда не будет >16K — кап мёртв.

## Post-hoc Premortem (ретроспектива выполненных работ)

Премортем применяется не только forward-looking (перед запуском), но и **post-hoc** — после выполнения работы, как ретроспектива.

**Когда использовать:**
- После завершения фазы/этапа (что пошло не так? что почти пошло не так?)
- Когда план был выполнен, но с отклонениями
- Когда хотим извлечь уроки до следующей фазы

**Отличие от forward premortem:**
- Фрейм: не «через 6 месяцев провалилось», а «мы только что сделали — что пошло не так и почему?»
- Причины не выдумываются, а извлекаются из логов, diff-ов, замеров времени
- Допущения проверяются фактами: запланированное время vs реальное

**Пример применения (из сессии 2026-05-03):**
Phase 1 план: 3.5 дня. Факт: 3 часа. Причина: не сделали recon перед планированием (не проверили реальный diff коммитов, не проверили существующие сервисы).

**Процесс:**
1. Собрать фактические данные: логи, git log, время выполнения
2. Сравнить план vs реальность в таблице
3. Для каждого расхождения >2x: «почему план ошибся?»
4. Какие риски из premortem сбылись/не сбылись и почему
5. Какие риски НЕ были в premortem, но проявились

## Pitfalls

- **Verify before claiming.** Не утверждай «план выполнен / всё работает» без проверки полного пути (browser → CF → nginx → сервис). Пользователь видит результат через инфраструктуру, не через localhost.
- **Recon before plan.** Перед оценкой времени проверь git log, ls services, pip list. 10x overestimation = бесполезный план.
- **Pure-LLM недостаточен.** Для production качества нужен pipeline: специализированные инструменты (NER, STT) + LLM (синтез). Не проектируй как «напиши промпт → всё сделает».
- **One-user blind spot.** Самое частое скрытое допущение в premortem: архитектура, работающая для 1 пользователя, будет работать для N. В реальности N пользователей — это не «1 пользователь × N», а N независимых систем с общим storage. Причины:
  - MEMORY.md как singleton не скейлится — per-user файлы или БД с user_id как partition key
  - state.db (SQLite) умирает на concurrent writes — PostgreSQL/ClickHouse для >100
  - hipporag один на всех = data leak; per-user = write amplification × N
  - inject всей памяти в system prompt упирается в context window
  - sync_turn() синхронно блокирует agent loop — async queue для >1 юзера
  - Нет user_id на уровне storage = GDPR nightmare, миграция переписывает слои
  - **1000 пользователей ≠ 1 мозг с 1000 памятей = шизофрения. Правильный фрейм: 1000 отдельных мозгов на общем железе.**
  - **Если план начинается с "agent stores memory in a file / SQLite / single index" — спроси "а если пользователей станет 1000?" на Шаге 1, до генерации причин.**

- **Log DB blind spot.** При анализе архитектур памяти AI-агентов — premortem часто не рассматривает observability-инструменты (ClickHouse, Loki, Elasticsearch) как решение. Признак: архитектура использует chromadb + hipporag + state.db + flat files + отдельный cache layer. Проверь: не решается ли задача одной log DB с TTL + materialized views + vector search? ClickHouse с 24.x умеет всё: `cosineDistance()` для RAG, `tokenbf_v1` для текстового поиска, `MATERIALIZED VIEW` для offline consolidation, `TTL` для забывания, `PARTITION BY user_id` для multi-tenant. Если premortem выявил 5+ кастомных компонентов для памяти — это сигнал "you're rebuilding log aggregation".

- **Write-time LLM annotation blind spot.** Самая распространённая ошибка при анализе архитектур памяти — рассматривать LLM только как **потребителя** памяти, а не как **активного аннотатора** на записи. Признак: архитектура предполагает offline consolidation (cron, materialized views, sleep replay) для извлечения паттернов. Проверь: может ли LLM аннотировать metadata (topic, importance, frequency, related_topics) в момент генерации ответа, до отправки пользователю? LLM уже обработал turn, понимает контекст, знает что повторяется, что важно, что связано. Metadata — побочный продукт генерации, zero additional tokens. Это collapsing impossible triangle: вместо offline consolidation → immediate annotation, вместо embedding scan → ORDER BY pre-computed weight. **Если архитектура для AI-агента использует "sleep replay" или offline consolidation для извлечения семантической памяти — спроси: "А что если LLM annotates на записи и это дешевле?" на Шаге 1.**

- **Cross-domain advice assumption trap.** Когда премортим советы данные для кого-то из другого домена/индустрии — каждое методологически верное утверждение несёт скрытые доменные допущения, которые не переносятся. Классический кейс (2026-05-07): советы по ML forecasting из трейдинга (MOEX) -> FMCG demand planning. Три допущения, которые убили план:
  - **Ground truth latency:** в трейдинге факт через 1 час, в FMCG через 2-4 недели. Evaluation loop для daily retraining не работает с monthly feedback.
  - **Feature semantics:** RSI/MACD для цен не эквивалентны промо-эффекту/каннибализации для спроса. Фичи не переносятся между доменами.
  - **Organisational context:** соло-трейдер (один принимает решения) не равен data analyst с annual goal без полномочий менять процессы.
  
  **Симптом:** премортим сгенерировал 10+ причин провала, и все они traceable к одному корню — "я дал совет из своего домена, не проверив его переносимость в домен собеседника".
  
  **Фикс:** Для КАЖДОГО пункта совета явно сформулируй: "Какое доменное допущение я делаю? Оно переносится?" Если не уверен — спроси пользователя до премортема. Добавь в Шаг 1 вопрос: "Из какого домена/индустрии берутся советы и в какой передаются?"

### Protection-mechanism degradation failure
Когда премортим анализирует план с protection mechanism (approval, guard, review gate, YOLO-mode override) — добавь как минимум одну причину провала: **механизм деградирует до нуля через override/disable**.

Классический паттерн:
1. Approval мешает работать — ставят YOLO-mode (disable)
2. YOLO-mode не выключают после задачи
3. Approval больше не работает, но иллюзия защиты остаётся
4. Через месяц — инцидент, который approval должен был поймать

**Фикс в премортеме:** Для любого плана с защитным механизмом спроси:
- «Что заставит пользователя выключить эту защиту?»
- «Как система предотвращает permanent disable?»
- «Какие сигналы покажут что защита выключена, даже если никто не помнит что её включали?»

См. `references/protection-degradation.md`.

### Subagent tool creep — deep-dive agents go rogue

Subagents for deep-dive analysis (Phase 4, Шаг 4) are given `terminal` + `file` + `search`
tools by default. They frequently go into independent research mode instead of analyzing
the assigned failure reason. This leads to 50+ tool calls, timeouts, and session
interruptions without producing the analysis.

**Symptoms:**
- Subagent starts checking file paths, configs, or session data that was
  already vetted in the main session
- Subagent re-discovers facts the main analysis already established
- 30+ tool calls in 3 minutes without producing any narrative output

**Prevention (доказано на практике):**
- **Проверенный приём:** `toolsets=[]` (пустой массив). Саб-агент без инструментов
  синтезирует исключительно из контекста промпта — ни одного лишнего вызова.
  Сработало 10/10 раз в сессии 2026-05-07 (premortem советов Чимиду).
- **Не используй `toolsets=["session_search"]`** — это даёт саб-агенту копаться в
  истории сессий вместо анализа задачи. Session search приводит к tool creep.
- Добавь в промпт саб-агента: "DO NOT research the codebase. Pure analysis only.
  Write 2-3 paragraphs. You have ALL the context you need in this prompt."
- Давай `terminal` + `file` ТОЛЬКО если анализ требует новых данных, которых нет в контексте.

**ВАЖНО: `toolsets=[]` применим ТОЛЬКО для narrative failure analysis (Шаг 4).**
Не переноси этот приём на Prism-анализ кода! Для code-review, Prism passes и
чтения PR diff-ов саб-агентам НУЖНЫ инструменты (`terminal`, `search_files`),
чтобы проверять exception hierarchy, существующие паттерны, импорты.
`toolsets=[]` для кодовых задач даёт findings без верификации — качество ниже.

**Когда какой подход:**
- Premortem deep-dive (чистый нарратив) → `toolsets=[]`
- Prism pass по коду (нужна верификация) → `toolsets=["all"]`
- Смешанный: Prism сначала, потом Premortem → первый с инструментами, второй без

**Fallback if still fails:**
- Synthesize directly from raw causes (Step 3 output) — you already have
  the list of failure reasons, you can write the narrative yourself.
- Format: why this cause kills the plan, what assumption it breaks, early warning signs.
- Quality will be ~80% of a good subagent, but 100% better than a timeout.
