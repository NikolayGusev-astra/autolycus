# Code-Change Premortem — Distinct Failure Patterns

## Когда это нужно

Премортем **кодового патча** (изменение одной константы, строки, логического условия)
отличается от премортема бизнес-плана или запуска продукта. Причины провала
количественно ограничены, чётко верифицируемы и traceable к конкретным строкам кода.

Используй когда объект премортема — коммит, PR, патч, не правка архитектуры.

## Типовые failure patterns для code-change premortems

Эти паттерны повторяются из раза в раз. Генерируй их автоматически, если объект —
техническое изменение:

### F1: Патч бьёт не в ту ветку кода
Самая частая ошибка. Автор фикса думает, что проблема в точке A, но на деле
выполнение уходит в точку B (условный переход, exception handler, другая ветка
`if/elif`). Результат: патч влит, но ничего не изменилось.

**Как ловить:** Перед премортемом прочитай код вокруг изменения — какие условные
ветки могут быть задействованы вместо изменяемой.

### F2: Корень не вылечен — лечится симптом
Патч меняет следствие, а не причину. Пример: увеличение буфера токенов вместо
установки `max_tokens` для reasoning models. Первый вызов всё равно валится,
стоимость ×3.

**Как ловить:** Спроси «если убрать этот патч, но починить причину — проблема
решится?» Если да — патч лечит симптом.

### F3: Upstream перетрёт
Изменение в файле, который форк регулярно синкает с upstream (run_agent.py,
model_tools.py, cli.py). Без механизма защиты (CI/CD patch, config-файл, обёртка)
патч бесследно исчезает при следующем `git merge`.

**Как ловить:** Проверь: это файл upstream или форковый (README/AGENTS.md)?
Если upstream — спроси «как патч выживет при следующем merge?»

### F4: Константа не подходит для всех провайдеров
Жёстко закодированное значение (262144 токенов, 256KB, 30s timeout) работает на
одном провайдере/модели, но ломает другой (Ollama, Anthropic, OpenRouter на
других моделях).

**Как ловить:** Пройдись по всем провайдерам и проверь: у каждого свой лимит?

### F5: Нет теста — рефакторинг уничтожит
Изменение не покрыто тестом. Через N месяцев другой разработчик (или сам автор)
рефакторит блок кода и бессознательно отменяет патч. Без теста — zero signals.

**Как ловить:** `pytest -k <keyword>` — сколько тестов падает?

### F6: Нет телеметрии — silent failure
Если патч не сработал (или сработал не так), система не производит диагностического
сигнала. Пользователь не знает, включена ли фича, сработала ли, упала ли.

**Как ловить:** Что будет в логах при срабатывании? При несрабатывании? А если
ничего не изменилось — как пользователь узнает?

### F7: Неявный рост затрат
Патч делает 3 API-вызова вместо 1, удваивает размер ответа, добавляет 200ms
задержки. Никто не заметит сразу, но через месяц — счёт ×3, пользователи злы.

**Как ловить:** Сравни cost-before vs cost-after для одного вызова.

### F8: Скрытое допущение — «если X, то Y» работает не так
Типично: «увеличим лимит → модель договорит». Но retry 2 и 3 несут накопленный
контекст (interim_msg, continue_msg) — модель тратит больше токенов на
перечитывание истории, буст частично съедается.

**Как ловить:** Для каждого причинно-следственного звена спроси: «а что если
причина порождает и побочный эффект, который ослабляет следствие?»

### F9: Промежуточная арифметика никогда не достигает финального капа
Изменение повышает финальный кап (32768 → 262144), но не проверяет, достигает
ли формула значения хотя бы старого капа. Пример (May 2026, run_agent.py):

```
_boost_base = self.max_tokens if self.max_tokens else 4096  # = 4096
_boost = _boost_base * (length_continue_retries + 1)        # 8192, 12288, 16384
self._ephemeral_max_output_tokens = min(_boost, 262144)     # → 8192, 12288, 16384
```

Кап 262144 **никогда не достигается** — максимальный буст 16K, что меньше даже
старого капа 32K. Патч меняет «дверь в башню», хотя «лифт не едет выше 16 этажа».

**Как ловить:** Найди минимально возможное значение входного параметра (`_boost_base`,
initial max_tokens, начальная константа). Пройди через КАЖДУЮ арифметическую операцию
до финального `min()`. Если промежуточный результат никогда не превышает старого капа —
F9 сработал. Не останавливайся на «кап повышен» — проверь, достигается ли он вообще.

**Типовые сценарии F9:**
- `max_tokens = None → fallback 4096` — буст никогда не даст >16K
- `retry_count = 3` — даже с коэффициентом ×N, 3 итерации не дадут >N×3
- `base * (retry + 1)` где base маленький — произведение растёт медленно
- `min(boost, CAP)` где boost << CAP — кап мёртвый, патч ничего не меняет

## Когда deep-dive агенты и HTML-отчёт не нужны

Code-change premortem обычно не требует:
- Subagent deep-dive по каждой причине (их 5-9, все содержательные и узкие)
- HTML-отчёта с карточками (синтеза в чате достаточно)
- Batch'инга (причины можно покрыть одним текстом)

**Достаточно:** raw причины + синтез (most likely / most dangerous / hidden
assumption / revised plan / checklist) — всё в одном сообщении чата.

**Исключения:** если патч меняет архитектуру (не константу/флаг) — тогда да,
нужен полный премортем.

## Шаг 1: что нужно для контекста

Для code-change premortem минимум:
1. Файл(ы) изменений, строка(ы)
2. Что было (исходный код)
3. Что стало (патч)
4. Стек провайдеров/моделей, на которых это работает
5. Режим API (chat_completions, anthropic_messages, bedrock_converse)

Всё это обычно уже в сообщении пользователя или в diff'е коммита.
Достаточно прочитать код вокруг изменяемых строк.
