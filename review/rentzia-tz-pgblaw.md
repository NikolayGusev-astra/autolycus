**Дата рецензии:** 2026-05-29  
**Документы:** README, ТЗ v2.0, Конституция v1.2, Архитектура v2.0, Вопросы к подрядчику

## Общая оценка

ТЗ детализировано: 5 документов, ~80 страниц, 13-разделная Конституция, вопросы для подрядчика. Выглядит солидно.

**Главная проблема:** ТЗ написано как «видиlegal ideal», а не как план разработки. В нём конфликты требований, нереалистичные ожидания и архитектурные мифы, которые приведут к провалу при прямом следовании.

**Готовность к передаче подрядчику: 3/10.** Требует переработки.

---

## 5 критических проблем

### 1. «Двухконтурная архитектура» — избыточность

**Написано:** Два физических контура. Сервер PБ Law внутри, VPS в Нидерландах снаружи, между ними — только обезличенные запросы.

**Реальность:** Заказчик уже в «внутреннем контуре» — локальный сервер, КонсультантПлюс, файлы дел. Построить второй периметр (VPS + reseller + анонимный аккаунт) — это +30-40% стоимости без прироста безопасности.

**Как должно быть:** Один сервер, один firewall. Локальная LLM для обработки приватных данных. Модуль анонимизации — программный, перед любым внешним запросом к Claude. Если Claude недоступен — система работает на локальной модели (хуже, но работает).

**Обоснование при бюджете «несколько миллионов»:** Две A6000 (по 48GB) + Qwen 3.5 32B/72B — полностью локальный инференс покрывает 90% задач. Cloud юридических рассуждений нужен не для «мощности», а для «качества кубического аргумента» на уникальных вопросах.

---

### 2. «Конституция» как system prompt — антипаттерн

**Написано:** 28 страниц, 13 разделов — от абсолютных запретов до спецпротоколов HNWI и трансграничных дел. Всё это — system prompt для модели.

**Реальность:** Ни одна LLM не удержит 28 страниц инструкций и не будет следовать им при длинном контексте. Модель будет «знать» правила, но нарушать их в стрессовых ситуациях. Это баг, а не фича.

**Как должно быть:**
- **Конституция** — документ для людей (аудит, compliance)
- **System prompt** — максимум 5-7 страниц ядра поведения
- **Intake, Self-review, чек-листы** — шаги workflow DAG, не текстовые инструкции
- **Guardrails** — отдельный модуль кода, проверяющий выход модели до показа Куратору

---

### 3. Модуль КП через ProjectMate — данные не готовы

**Написано:** ИИ анализирует обращение → ищет аналоги в ProjectMate → рассчитывает трудозатраты → генерирует КП → шлифует через Claude.

**Реальность:** ProjectMate содержит **свободный текст** отчётов без классификации. Нормализация через LLM — это угадайка ±50%. Ни одна модель не даст точную оценку по разнородным аналогам.

**Рекомендация:**
1. **Сначала:** разметить 20-30 пилотных проектов ProjectMate вручную + LLM
2. **Потом:** строить расчётный движок на структурированных данных
3. **Модель** даёт вилку (P25-P75), **Куратор** корректирует
4. **Генерация КП** — шаблонизатор + LLM для тезисов

---

### 4. RAG на «архиве за десятилетия» — требует подготовки

**Написано:** Загрузить весь архив PБ Law (сканы, PDF, DOCX, бумага) с метаданными и изоляцией по делам.

**Реальность:** Это десятки гигабайтов неструктурированных данных. «Загрузить в RAG» — 2-3 месяца OCR, чистки, чанкинга, разметки.

**Рекомендация:**
- MVP — на 50-100 лучших заключениях/шаблонах
- Полная загрузка архива — фаза 2 (3-6 мес)

---

### 5. «Интеграция» с КонсультантПлюс / Casebook = ручной труд

**Написано:** "Гибридный workflow" — помощник делает выгрузки по запросу.

**Реальность:** Не интеграция, а ручная работа. 10-30 минут на запрос. Смысл автоматизации пропадает.

**Рекомендация:** Честно прописать как MVP-ограничение. Система формирует запрос → человек выполняет. API — целевое состояние, но не блокер MVP.

## Конфликты в требованиях

| Конфликт | Суть | Риск |
|---|---|---|
| Качество vs Конфиденциальность | Claude нужна фактура, но фактуру нельзя отправить | Либо утечка, либо стерильные запросы |
| Полнота vs Скорость Intake | Система не стартует без полных данных, но Куратор не может дать всё сразу | Юристы обходят Intake |
| Качество LLM vs Бюджет | Qwen 72B требует A6000, но бюджет в ТЗ не специфицирован | Непонимание на старте |

## Пробелы, которые нужно закрыть до понедельника

1. **Бюджет:** «несколько миллионов» — какой диапазон? 3-5М? 5-10М?
2. **Сроки:** когда нужен MVP?
3. **Данные:** сколько документов в архиве? какой формат?
4. **ProjectMate:** на чём работает? какой объём?
5. **Пользователи:** сколько одновременных сессий?
6. **Приёмка:** какие KPI успеха?

## Рекомендуемый roadmap (при бюджете 3-5 млн)

### Фаза 0 — Подготовка (1-2 мес)
- Аудит данных (RAG-ready, ProjectMate)
- Разметка 20-30 пилотных проектов ProjectMate
- NDA с подрядчиком

### Фаза 1 — MVP (3-4 мес)
- Локальный сервер (одна A6000 на MVP, вторая — на фазу 2)
- Qwen 3.5 32B локально
- RAG на 50-100 документах
- Intake + workflow DAG
- Модуль анонимизации → Claude API
- Self-review guardrails
- Веб-интерфейс (создание дело → задача → проверка)
- Аудит-лог

### Фаза 2 — Расширение (3-6 мес)
- Вторая A6000 → Qwen 72B или fine-tune
- Полный RAG-архив
- Модуль КП + ProjectMate
- Casebook интеграция (при наличии API)

## Стоп-критерии для подрядчика

Подрядчик не подходит, если:
- ❌ Не понимает двухконтурную модель
- ❌ Предлагает "отказаться от двухконтура для упрощения"
- ❌ Парсит КонсультантПлюс / использует headless browser для Casebook
- ❌ Не может объяснить, как технически не допустить утечки
- ❌ Vendor lock-in («наше проприетарное решение»)
- ❌ Обещает «точный расчёт трудозатрат через AI»
