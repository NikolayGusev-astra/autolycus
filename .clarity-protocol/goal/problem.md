## 1. Фрейминг проблемы

### Что заявлено как цель
Создание внутренней системы ИИ-юриста для адвокатского бюро PGB Law, которая работает под руководством адвоката-куратора.

### Давление на фрейминг: что реально нужно

Если приложить «волшебную палочку» и система уже работает — что заказчик получает?

**Реальная бизнес-цель первого уровня:**
- Рост производительности юристов (больше дел на одного партнёра)
- Сокращение времени на рутинные задачи (анализ документов, поиск практики, подготовка КП)
- Повышение качества через систематическую проверку (self-review, чек-листы)

**Реальная бизнес-цель второго уровня:**
- Повышение конкурентоспособности за счёт более быстрой подготовки КП с точной оценкой трудозатрат
- Накопление и повторное использование знаний Бюро (RAG-база)
- Защита репутации Бюро через контроль качества

**Реальная бизнес-цель третьего уровня (защитная):**
- Недопустимость утечки адвокатской тайны (репутационный и правовой риск)
- Соответствие ст. 8 ФЗ №63-ФЗ и Кодексу профессиональной этики адвокатов

### Является ли «ИИ-юрист» целью или средством?

Средство. Истинная цель — **система поддержки принятия решений юристом** с жёсткими гарантиями конфиденциальности.

## 2. Разделение проблемы от решения

В ТЗ есть overspecification — заказчик зафиксировал конкретное техническое решение как требование:

| Заявленное требование | Реальная проблема |
|---|---|
| Двухконтурная архитектура | Недопустимость утечки клиентских данных во внешние сервисы |
| Локальная LLM (Qwen/DeepSeek/Llama) | Обработка приватных данных без их покидания сервера |
| Claude API через обвязку | Нужда в качественном юридическом рассуждении, которое локальные модели пока хуже дают |
| Обязательный Intake-протокол | Недопустимость работы без полных входных данных (качество + ответственность) |
| Гибридный workflow с КонсультантПлюс | Невозможность прямой интеграции из-за лицензионных ограничений |
| RAG на Qdrant/RAG | Накопление и повторное использование знаний Бюро |
| Модуль КП с ProjectMate | Точность оценки трудозатрат через исторические данные |
| LangGraph/n8n для оркестрации | Контролируемый воркфлоу с точками человеческой проверки |

**Критический вывод:** Двухконтурная архитектура — это не «фича», а **фундаментальное ограничение**, вытекающее из правовых требований. Это не предмет для обсуждения на этапе проектирования — это константа.

## 3. Конфликты и противоречия в требованиях

### Конфликт 1: Качество vs Конфиденциальность
- **Требование качества:** Claude нужен для «тонкого юридического рассуждения» — это требует передачи фактуры
- **Требование конфиденциальности:** Никакая фактура не должна покидать внутренний контур
- **Решение в ТЗ:** Декомпозиция + обезличивание. Но: качество обезличивания зависит от качества локальной модели
- **Риск:** Если локальная модель плохо обезличивает — утечка; если переобезличирует — теряется смысл запроса

### Конфликт 2: Полнота vs Скорость Intake
- **Требование:** Система не начинает работу, пока не собран полный пакет данных (§3.2 Конституции)
- **Реальность:** На практике Куратор не всегда может предоставить все данные сразу
- **Решение в ТЗ:** Перечень запросов Куратору + остановка. Но: это замедляет процесс
- **Риск:** Сопротивление пользователей — юристы будут обходить Intake или заполнять формально

### Конфликт 3: Автономия vs Контроль
- **Требование:** ИИ готовит — Куратор подписывает (§1.3 ТЗ)
- **Требование:** Для критичных дел — ручная проверка обезличенных подзапросов перед отправкой (§11.7 Конституции)
- **Реальность:** Управляющий партнёр — единственный человек, который подписывает КП (§12-В.5)
- **Риск:** Бутылочное горлышко — если Куратор должен проверять всё, падает производительность

### Конфликт 4: Качество локальной модели vs Бюджет
- **Требование:** Контекстное окно 128K токенов, качественный русский язык, RAG, следование длинному system prompt (§3.1 ТЗ)
- **Рекомендация:** Qwen 2.5 72B или DeepSeek V3 — это требует 1-2 GPU A6000 (48GB VRAM)
- **Риск:** Стоимость железа ~700K-1.5M руб + обслуживание

## 4. Открытые вопросы (требуют уточнения)

1. **Бюджетный диапазон:** ТЗ содержит требования к железу и техническим характеристикам, но бюджет проекта нигде не указан. Это критический пробел для оценки реализуемости.

2. **Сроки внедрения:** Отсутствует временной график — нет формулировки «когда должно быть готово MVP».

3. **Объём данных для RAG:** Указано «архив за десятилетия» — но не объём (сколько документов? какой объём в ГБ?).

4. **Текущее состояние ProjectMate:** Структура данных не описана — свободный текст требует нормализации.

5. **Количество одновременных пользователей:** 20+ профессионалов — но сколько одновременных сессий?

6. **Резервный план при недоступности Claude:** Упомянут «другой reseller» и «DeepSeek API», но нет детализации.
