## Ключевые выводы

### 1. Задача определена чётко, но с overspecification
Заказчик отлично понимает проблему. ТЗ детализировано до уровня конкретных моделей (Qwen 2.5 72B) и фреймворков (LangGraph). Это плюс — снижает риски непонимания. Минус — ограничяет свободу подрядчика в выборе оптимального решения.

### 2. Двухконтурная архитектура — не опция, а константа
Правовое требование (адвокатская тайна) однозначно диктует двухконтурность. Это не предмет для trade-off анализа — это фиксированное ограничение.

### 3. Главный риск — качество обезличивания
Весь двуконтурный дизайн зависит от одного предположения: локальная LLM достаточно хорошо обезличивает данные. Если нет — либо утечка (F-01), либо бесполезные запросы к Claude (F-04).

### 4. Архитектура зрелая, но есть пробелы
ТЗ покрывает ~85% требований. Пробелы:
- Бюджет не указан
- Сроки не указаны
- Кол-во пользователей не специфицировано
- Disaster recovery не описан
- Миграция данных ProjectMate требует уточнения

### 5. Модуль КП — самая сложная часть
Требует: ProjectMate интеграция + нормализация свободного текста + расчётный движок + генерация с обезличивеванием + stylebook. Это ~40% сложности проекта.

## Стейкхолдеры: ключевые инсайты

1. **Куратор** — критический пользователь, который не techie → интерфейс должен быть интуитивным
2. **Клиенты (Forbes)** косвенный stakeholder с критическим влиянием → любая утечка = катастрофа
3. **Подрядчик** — aligned + adversarial → NDA + синтетические данные + аудит

## Рекомендации

### Немедленные (перед запуском проекта)
1. **Red teaming обезличивания** — до подписания с подрядчиком, протестировать на реальных кейсах
2. **Определить бюджет** — без этого невозможно выбрать железо и оценивать подрядчиков
3. **Написать NDA** — до передачи документов подрядчику

### На этапе проектирования
4. **LangGraph** для оркестрации (агентный DAG с human-in-the-loop)
5. **Qdrant** для RAG (локальный, быстрый)
6. **MVP без модуля КП** — сначала core (Intake + RAG + Claude), потом КП

### На этапе разработки
7. **Синтетические данные** для разработки и тестирования (не реальные дела!)
8. **A/B тестирование обезличивания** — сравнить несколько моделей/prompts
9. **Пилот на 1-2 Кураторах** перед rollout на весь офис

### Стоп-критерии для подрядчика (из документа «Вопросы»)
- ❌ Не понимает двухконтурную архитектуру → отказ
- ❌ Предлагает «упростить» за счёт отказа от двухконтурности → отказ
- ❌ Предлагает парсить КонсультантПлюс/Casebook → отказ (нарушение лицензии)
- ❌ Не может объяснить техническую защиту от утечки → отказ
- ❌ Vendor lock-in («наше уникальное решение») → отказ
