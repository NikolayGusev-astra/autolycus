## Записи решений

### DEC-001: Один контур вместо двух
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** ТЗ требовал двухконтурную архитектуру (сервер PGB Law + VPS в Нидерландах). Анализ показал: один контур + программный модуль анонимизации = compliance + проще + дешевле.
- **Решение:** Один сервер (2× A6000), один firewall. Qwen 3.7 локально для всех задач. Модуль анонимизации (Natasha NER + правила) для любых внешних запросов.
- **Последствия:** -60% сложности, -70% OpEx, TCO 2.1M ₽ vs 3.5M ₽ (3 года)
- **Связанные документы:** goal/problem.md, solution/solution.md
- **Триггеры пересмотра:** появление требования регулятора о физическом разделении

### DEC-002: Compact Constitution + RAG
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** 15K токенов Конституции как system prompt неэффективны (lost-in-the-middle, attention sink).
- **Решение:** Compact Constitution (500-800 токенов) = идентичность + 7 запретов + 6 принципов. Полный текст в RAG с тегированием по разделам.
- **Последствия:** Экономия 50-70% токенов. Точность доступа к разделам выше через RAG.
- **Связанные документы:** goal/requirements.md

### DEC-003: Pipeline-обезличивание
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** Обезличивание через 72B LLM — расточительно и ненадёжно.
- **Решение:** Natasha NER (детерминированный) + Qwen 2.5 7B fine-tuned (контекстуальный) + валидатор. MVP: NER + правила без fine-tuning.
- **Последствия:** Детерминированность, проверяемость. Отдельная малая модель вместо гоняния 72B.
- **Связанные документы:** solution/solution.md
- **Триггеры пересмотра:** Результаты первого red teaming обезличивания

### DEC-004: Hermes-оркестрация (DAG)
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** Монолитная LLM «делает всё» → непредсказуемость, отсутствие контроля.
- **Решение:** DAG-оркестратор с атомарными агентами: Intake → Decomposition → Obfuscation → Research → Assembly → Self-review. Human-in-the-loop на ключевых точках.
- **Последствия:** Модульность, ремонтопригодность, прозрачность для Куратора.
- **Связанные документы:** solution/solution.md

### DEC-005: Guardrails через пост-процессинг
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** Self-review как prompt инструкция ненадёжна.
- **Решение:** 4 детерминированного чекера (citation, name leakage, confidence, format) + LLM-as-judge внешний.
- **Последствия:** Блокировка ответа при нарушении. Задержка выдачи 10-30 сек.
- **Связанные документы:** failures/failures.md

### DEC-006: Qwen 3.7
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** ADR-001 ссылался на Qwen 3.6, которого ещё не было. Вышел Qwen 3.7.
- **Решение:** Qwen 3.7 как целевая модель. MVP на 3.6/3.7 32B, миграция на 72B после тестирования. Fine-tune 2.5 7B для обезличивания.
- **Последствия:** Актуальный стек. Нет зависимости от будущих релизов.

### DEC-007: ProjectMate prerequisite
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** Свободный текст отчётов ProjectMate не пригоден для ML без структурирования.
- **Решение:** ProjectMate интеграция НЕ входит в MVP. Prerequisite: разметка 50-100 проектов + нормализация.
- **Последствия:** MVP без модуля КП. Модуль КП — фаза 2 (3-6 мес после MVP).
- **Связанные документы:** goal/problem.md

### DEC-008: MVP scope — честные ограничения
- **Статус:** decided
- **Дата:** 2026-05-29
- **Контекст:** Ожидать всего сразу = провал проекта.
- **Решение:** MVP = Intake + Research + Assembly + Self-review + RAG (ручная загрузка) + аудит-лог. Ручные выгрузки КП. Без ProjectMate, без Claude API.
- **Последствии:** Реалистичные сроки. Проверка value hypothesis перед инвестицией в расширение.
- **Связанные документы:** goal/requirements.md, goal/problem.md
